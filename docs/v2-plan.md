# codesys-mcp-toolkit v2 — Step 0 findings and rewrite plan

Status (2026-11-07): Phase 0 spike done, Phase 1 core done, Phase 2 simulation (text) done, Phase 3 read-only panel done. Phase 4 (interactive panel) not started.

## 1. Summary

v1 is replaced, not patched. v2 is an ESM TypeScript MCP server with a
persistent CODESYS bridge, an ST-only tool set, and a truST-backed simulation
layer with an MCP App panel on top. The CODESYS bridge copies proven designs
from other projects; the simulation panel is the part nobody else has.

## 2. What Step 0 found

### 2.1 This repo (v1)
- **Two diverged baselines.** GitHub `main` / npm 1.1.16 is the 1.1.3 code
  (all Python inlined in `server.ts`). Local `main` carries two unpushed
  "Refactored the code" commits (1.1.4: `src/scripts/*.py`, session files) —
  the refactor upstream reverted because POU creation broke. Claude Desktop on
  this machine runs the npm 1.1.16 build.
- **Every call cold-starts CODESYS** (`CODESYS.exe --runscript=tmp.py`).
  The "persistent session" mode is a stub: `executeScript` in
  `codesys_session.ts` still calls `executeCodesysScript`, and
  `start_session.py` uses f-strings, which IronPython 2.7 cannot parse.
- **Scripts are generated by string interpolation** and written as `latin1`
  with no coding header — non-ASCII text breaks (PR #9).
- **`compile_project` never reports errors** — it prints "compilation
  initiated" and exits (PR #10).
- **Reads are resources only** (`project-structure`, `pou-code`), which Claude
  Desktop doesn't expose to the model (issue #6).
- `@modelcontextprotocol/sdk` ^1.10.2, CommonJS, no tests, no CI tests.

### 2.3 Other CODESYS MCP projects
- **CODESYS SP22 Patch 1 ships its own MCP server** (separate license, 19
  tools, named-pipe plugin). This machine has SP21. Ignore for now; possible
  later backend.
- **zbest1000/mcptoolkit-for-codesys** (Python, MIT) — most robust bridge:
  persistent CODESYS running a watcher with preloaded op handlers, JSON
  `{op,args}` requests over a file queue, heartbeat file (idle/busy+deadline)
  with healthy/hung/dead detection and respawn, `system.prompt_handling` to
  suppress modals, `confirm:true` on online writes.
- **phobicdotno/Codesys-MCP-Master** (TS, MIT, 132 tools) — WinForms timer on
  the UI thread so the runscript returns and menus stay usable; routes to the
  CODESYS install matching the project's version; refuses SP conversion;
  already has `mirror_export` and PLCopen import/export.
- **luke-harriman/Codesys-MCP** — breaks on SP21+ because
  `execute_on_primary_thread` was removed.
- **None of them can switch off online tools** (login/download/write/force).

### 2.4 truST (trust-platform — your repo)
- Rust, MIT/Apache, v0.33.0 (2026-11-06), prebuilt Windows zip; native AOT
  needs a ~216 MB pinned toolchain bundle.
- **Simulation:** `trust-runtime play --simulation --time-scale 1..100`;
  sim time advances exactly one cycle per scan (never wall clock).
- **Debug:** `trust-debug` DAP over stdio — conditional/hit-count breakpoints,
  logpoints, step in/over/out, setVariable/force, pause. Needs a debug image.
- **Control endpoint:** NDJSON over `tcp://127.0.0.1` + per-start token —
  `status`, `var.force/unforce`, `io.*`, `pause/resume`, `cycle.step`,
  `config.set`. Also `trust-dev agent serve` (JSON-RPC stdio).
- **Plant models** live in `simulation.toml`: `gravity_tank`, `first_order`,
  `integrator`, … with noise, disturbances/faults, actuator limits; lockstep
  with scans. **Wired by `%I/%Q` address only.** `libraries/plant` is
  PLC-side equipment FBs, not process models.
- **CODESYS profile** (`vendor_profile = "codesys"`) is two weeks old. Parser
  has METHOD, PROPERTY GET/SET (nested inside the FB), INTERFACE, EXTENDS,
  IMPLEMENTS, THIS/SUPER, POINTER/REFERENCE, UNION, VAR_STAT, ACTION.
  **Missing:** VAR_INST, FB_init/FB_exit, `__ISVALIDREF`, `__QUERYINTERFACE`,
  `__TRY`; pragmas ignored except `qualified_only`; no Util/CAA/SysLib.
- **PLCopen import drops property GET/SET bodies** (replaced by stubs,
  `PLCO225`). → The mirror must compose ST text directly, not go through
  PLCopen.
- **Unsafe defaults:** web UI on `0.0.0.0:8080` and discovery are ON; with no
  `io.toml` it falls back to machine I/O. Simulation mode rejects physical
  drivers. v2 must write these configs explicitly.

### 2.5 MCP Apps
- Spec stable (2026-01-26). `@modelcontextprotocol/ext-apps` 2.0.4 needs SDK
  v2 split packages + zod 4; 1.7.5 needs SDK ≥1.29. **ESM only.**
- UI = `ui://` resource, `text/html;profile=mcp-app`, linked via
  `_meta.ui.resourceUri`; single-file HTML (Vite + singlefile); CSP via
  `_meta.ui.csp`, external origins blocked by default.
- App-only tools: `_meta.ui.visibility: ["app"]`.
- **No server→app push: poll** (official example: 2 s). Plan ~4 Hz with
  delta events, not 10 Hz.
- **Every tool call mounts a new panel and old ones keep running** → use the
  documented supersession pattern (seq + BroadcastChannel) so only the newest
  panel polls.
- `updateModelContext` overwrites; host may deliver it only with the next user
  message. Claude Desktop renders apps from local stdio servers.
- Gate UI registration on the host's `io.modelcontextprotocol/ui` capability;
  every tool returns useful text regardless.

## 3. Decisions

### 3.1 Scope
- **ST only.** Supported objects: Program, FB, Function, Method, Property
  (GET/SET), Action, Interface, DUT (struct/enum/union/alias), GVL. Non-ST
  objects (SFC, CFC, LD, FBD, IL) are detected and reported, never edited;
  the simulator refuses to run code that calls them unless stubbed explicitly.
- **No online tools.** v2 never logs in, downloads, writes or forces on a
  controller. Enforced by having no such ops in the watcher at all, so the
  simulation rule holds by construction.
- **SP22 built-in MCP server:** not used.

### 3.2 CODESYS bridge (copying zbest + Master)
- One persistent CODESYS per server, started with `--runscript=watcher.py`
  (scripts staged to a local folder; UNC paths silently fail).
- Watcher = preloaded op handlers; requests are JSON `{id, op, args}` files,
  written tmp+rename; results likewise. **No generated Python** — removes
  injection and input-encoding bugs.
- UI-thread WinForms timer (Master) so the IDE stays usable; `system.delay()`
  loop for `--noUI`.
- Heartbeat file with current op + deadline; host classifies
  healthy/hung/dead, kills and respawns; adopts a live watcher on restart.
- `system.prompt_handling` set at startup; watcher exits when the server's PID
  dies.
- UTF-8 everywhere: `codecs.open(..., 'utf-8-sig')`, decode fallbacks
  utf-8 → mbcs → latin-1, `ensure_ascii=False`, ASCII-only watcher source.
- Version routing: detect CODESYS installs, refuse to open a project in a
  different SP (avoids silent conversion).
- `health` / `diagnose` answer without waiting on the watcher.

### 3.3 Stack
- ESM, TypeScript, Node ≥20, MCP SDK v2 split packages + ext-apps 2 + zod 4.
- vitest; a mock watcher (Python 3) for tests without CODESYS; live tests
  gated by an env var; GitHub Actions on windows-latest.
- Panel: Vite + vite-plugin-singlefile, CodeMirror 6, plain SVG for P&ID,
  small canvas trend.

### 3.4 truST integration
- Pin one truST version; check it at startup.
- **Mirror composes ST text directly** (FB file with nested METHOD/PROPERTY/
  ACTION blocks), one file per top-level object, plus generated
  `runtime.toml` (web/discovery off, debug image), `io.toml`
  (`driver = "simulated"`), `simulation.toml`, and `Configuration.st`.
- **Symbolic plant wiring:** `plant.toml` maps plant signals to ST variable
  names; v2 generates `%I/%Q` addresses + `VAR_CONFIG`/`AT` mapping and the
  matching `simulation.toml`. (Alternative: add symbolic wiring to truST.)
- Control: runtime control endpoint for run/pause/step/force/read/time-scale;
  `trust-debug` (DAP, stdio) for breakpoints and stepping.
- Since you own truST, gaps can be fixed there instead of worked around:
  properties in PLCopen import, VAR_INST, FB_init, symbolic plant wiring,
  explicit "plant frozen while halted" guarantee.

## 7. Phase 0 spike results (2026-11-07)

Verdict: **go.** truST can simulate CODESYS ST once the gaps in
[`spike/trust-fidelity/TRUST-GAPS.md`](../spike/trust-fidelity/TRUST-GAPS.md)
are fixed in truST. The spike ran the full path (CODESYS SP21 → export →
composed mirror → truST build → closed loop with the `gravity_tank` plant →
breakpoint, step, force, interlock trip) with three source workarounds:
`E.X` → `E#X`, `VAR_INST` → `VAR`, and `__ISVALIDREF` removed.

What changes in the plan:
- **Use the runtime control endpoint for everything, not DAP.** It already has
  breakpoints, step in/over/out, pause/resume, eval, force, and stack/variable
  reads. DAP is needed only until truST exposes expression compilation for
  conditional breakpoints (gap B1).
- **The plant freezes at a breakpoint.** Verified: the level was unchanged for
  3 s of wall time while paused. No extra work needed.
- **The mirror approach holds.** Composing ST text directly (not PLCopen)
  keeps property bodies. The rules the mirror needs are listed in
  TRUST-GAPS §C.
- **CODESYS bridge facts for v2:**
  - Cold start ~138 s, warm ~17 s. That confirms the persistent bridge.
  - Stdout only reaches the caller when CODESYS isn't started with redirection.
  - Object names are localised ("Taskkonfiguration"), so identify objects by
    type GUID.
  - SP21 has `system.prompt_handling` but not the newer
    `script_prompt_handling`, so probe for both.
  - `build()` only compiles POUs a task reaches.
  - Read messages right after `build()`, because any later build
    (`check_all_pool_objects`) wipes them.
  - Errors carry object + parent + `position_text` ("Line 1, Column 1 (Impl)").
  - `create_interface()` adds `EXTENDS __System.IQueryInterface`.
  - Task items in `task.pous` are plain strings.
- **truST `build` needs its toolchain** (~181 MB, auto-installed). v2's
  `sim_start` must check `toolchain status` first and ask.
- **Rebuild takes ~35 s** for the tank project, so experiments that only change
  parameters should use `force` / `config.set`, not rebuilds.

Spike files: `spike/trust-fidelity/` (CODESYS script `cds_spike.py`,
`compose_mirror.py`, `trust-template/`, `repros/` + `run_repro.py`).

## 8. Phase 2 results (2026-11-07)

Done: the acceptance demo steps 1-2, 4-5 and 7-8 run as text, through the MCP
tools, against real CODESYS SP21 and truST 0.33 (`test/live/sim.live.test.ts`).
The same flow runs against truST alone with a faked CODESYS export
(`test/sim-trust.test.ts`, skipped when truST isn't installed).

Code: `src/sim/` (mirror, plant, runtime, control client, controller, tools).

Decisions made while building it:
- **The control endpoint only, no DAP.** Breakpoints, stepping, the stack,
  locals, forcing and the time scale all work over NDJSON on 127.0.0.1 with a
  per-start token.
- **Paused between calls.** `run_scans` is exact: a hit-count breakpoint sits
  on the scan counter of a generated harness program that runs first in the
  fastest task.
- **CODESYS paths in truST.** Program instances get their POU's own name, so
  `PRG_Tank.nTrips` works in both. Breakpoints and build errors use CODESYS
  object lines through the mirror's line map.
- **Symbolic plant wiring.** `plant.toml` wires plants by variable name, and
  the mirror generates the AT addresses. Plant-fed variables are forced
  through `io.force` (TRUST-GAPS B17).
- **Enum literals.** The mirror rewrites `E.X` to `E#X`. CODESYS SP21 rejects
  `E#X` and truST rejects `E.X` (A1), so there is no common form.
- **Conditions in the toolkit** until truST compiles condition text (B1, B19).
- **Experiments restart the process.** truST's control restart doesn't reset
  plants (B13) and it can't start paused (B14). A fresh start always completes
  one scan before handing over.
- **Safety.** `src/sim/` reads CODESYS only through `export` and `tasks.list`,
  and the controller module has no access to the bridge. A test checks this.
  Before every start the toolkit checks for simulated I/O, simulation enabled,
  web, discovery and mesh off, and a loopback control endpoint, and truST
  always runs with `--simulation`.

New truST gaps: B11-B19 in TRUST-GAPS.md.

## 9. Phase 3 results (2026-11-07)

Done: `open_sim_panel` shows a live, read-only panel (MCP App). A live
experiment animates the tank and fills the trend. A breakpoint stop
highlights the line in the CODESYS code. Checked in the dev host
(`scripts/dev-host/`, which embeds the panel with the ext-apps AppBridge like a
real host) in light and dark themes, plus `test/panel.test.ts` and panel
checks in `test/sim-trust.test.ts`.

Decisions:
- **Vanilla TypeScript + esbuild, no Vite or CodeMirror.** A read-only code
  view with a gutter is a few lines of DOM. The single-file panel is 415 kB,
  mostly the ext-apps App class and its protocol code. zod's non-English
  locales are stubbed out, which saves 250 kB.
- **Polling at 4 Hz while something runs, 1 Hz otherwise.** The panel tools are
  read-only towards truST: they never drain stop records or change the run
  state, so they are safe while a model tool runs.
- **Supersession on the server.** The newest `open_sim_panel` id wins, and
  older panels get `current: false` and stop. (BroadcastChannel is unreliable
  across sandboxed iframes.)
- **Trend recorder in the controller.** It samples at the end of every run,
  at every experiment sample, and on live polls. Each fresh start begins a new
  epoch.
- **The P&ID is generic, built from `plant.toml`:** a tank for tank models;
  valves and pumps recognised from `[[feedback]]` names (`XV…`, `P101`).
  `display = { max, unit, label }` sets the scale.
- **App-only tools are disabled** for clients without the
  `io.modelcontextprotocol/ui` capability.
- **Code shown as written in CODESYS:** the mirror's `E#X` is mapped back to
  `E.X` for display.

Not checked: inside Claude Desktop itself. That needs the user's Claude
Desktop pointed at this build.

## 10. Revised roadmap (2026-11-07)

### Why

The Phase 3 panel puts code, plant and I/O on one screen. That works for the
tank example (5 objects, 6 signals). A real project has hundreds of POUs,
several tasks and thousands of I/O points. Two audiences need different
things:

- **The user**, who watches and reviews:
  - where Claude is working (a project tree);
  - what Claude changed (a diff per object);
  - whether the code does the right thing (live values in the code, a scoped
    watch list);
  - how the process behaves (plant, trends), on demand.
- **Claude**, who writes the program from a prompt:
  - the project's structure without reading every file (outline,
    cross-references, interfaces, task assignment);
  - fast proof that the code works (unit tests and regression scenarios);
  - real library signatures;
  - a change set with checkpoints;
  - what the user is looking at.

Both should read the same facts: the symbol table, test results, the change
log, and the live values of a chosen set of variables.

### Phase 5: tools for Claude

| Tool | What it gives | Source |
| --- | --- | --- |
| `get_outline` | Per POU: kind, interface (inputs, outputs, in-outs), methods and properties with signatures, task | mirror + trust-lsp document symbols, or a parse of the export |
| `find_references` | Where a variable, FB or method is declared, read, written and called, in CODESYS paths and lines | trust-lsp references on the mirror |
| `get_call_graph` | Who calls whom, from the tasks down | references |
| `run_tests` | Unit tests for FBs in simulation: pass/fail with the failing assertion | truST test programs, if supported (see 10.1) |
| `run_scenarios` | Saved experiments and interlock checks, rerun after every change, with regressions flagged | experiments stored with the project |
| `get_library_api` | Real signatures of library FBs and functions | CODESYS library manager (scripting) |
| `get_changes` / `revert_object` / checkpoints | What changed in this session, per object, with revert | snapshots of the exported ST (the mirror's git history covers the simulation side) |
| `get_io_list` | I/O with comments, units and ranges; later the device I/O mapping | declarations, then the CODESYS device tree |

Tool results stay compact (summaries, paging), because a large project must
not flood the model's context.

### Phase 6: workspace

- **An in-chat card** (the current panel, slimmed down): what Claude is doing,
  the current object, the last test and experiment result, a few key signals,
  and "Open workspace".
- **A full-screen workspace** with the CODESYS layout:
  - **Left:** the project tree, with badges for changed, compile error,
    breakpoint, stopped here, not simulated, and Claude editing now.
  - **Center:** editor tabs, with declaration above implementation, live
    values inline (like CODESYS online mode) and a diff toggle against the
    session start.
  - **Right inspector:** watch list, locals and call stack, breakpoints, I/O
    scoped to the open POU.
  - **Bottom tabs:** trend (chosen signals, experiment overlays), plant,
    tests, activity (what Claude did, in order), problems.
- **"Follow Claude" toggle:** the view follows where Claude works, or stays
  where the user is reading.
- **Lazy loading:** the tree first, sources per object when opened, values
  only for visible and pinned variables.
- **Model context:** the panel tells Claude what the user selected
  (MCP Apps model-context update), so "fix this" refers to what is on screen.
- **To check:** whether Claude Desktop supports the MCP Apps full-screen
  display mode. If not, the workspace works inline with collapsible regions.

**Status (2026-11-07): done, read-only.** One panel with two layouts, picked
from the host's display mode:
- **In the chat:** a compact card.
- **Full screen:** the workspace. Where the host has no full screen, it
  expands inline instead.

Verified in the dev host, which acts as a full-screen-capable host through
the ext-apps AppBridge:
- a breakpoint stop opens `PRG_Tank` at line 11 with inline values;
- Claude's edit of `FB_PI` opens with an M badge and a correct diff;
- compile problems link to their objects;
- clicking a line sends "the user selected FB_PI implementation line 5: …"
  as model context.

Design decision: **the panel never calls CODESYS.** The bridge is serial, so
panel polling would stall the model's tools. Instead the tools keep a
`ProjectCache` current as a side effect of their own calls (open, export,
read, write, create, delete, rename, revert, compile, and the simulation's
sync), and the workspace reads that. The cache carries a version, so polling
is cheap when nothing changed.

Not verified: Claude Desktop's own full-screen support. The panel falls back
to expanding inline.

### Phase 7: interaction (the old Phase 4)

On top of the workspace:
- clicking the gutter sets a breakpoint;
- step and continue buttons;
- forcing from the watch list;
- plant sliders;
- "pause Claude";
- accept or revert per object from the diff.

**Status (2026-11-07): done.** "Plant sliders" became a parameter form,
because truST applies plant changes only on restart: a slider would restart
the simulation on every move. The form applies a batch with one restart.

How it works:
- **User actions** are app-only `ui_*` tools. They answer `{ok, message}`
  instead of failing, and the panel shows the message as a toast. Each
  action is journaled as "User: …". The panel also sends the last few
  actions to Claude as model context.
- **While Claude is busy** (a run, an experiment), actions that would fight
  it are refused. Pause, breakpoints, hold, accept and revert still work.
- **Continue** runs in the background, so the panel stays live. Pause
  interrupts it at the next stop check.
- **Pause Claude** is a `Driver` flag. A wrapper on tool registration holds
  the tools that change the project (write/create/delete/rename/revert,
  libraries, project open/close/create) or the simulation (start/stop/run,
  breakpoints, stepping, writes, forces, plant, experiments, scenarios). A
  held tool answers `paused_by_user` with how to proceed. Reading tools,
  compile and tests are not held.
- **Review:** sessionStart saves a `review` checkpoint next to
  `session-start`. Accept replaces one object's subtree in it. The badges
  and diffs compare with it, and Revert restores it through the same code
  as `revert_object`. Claude's `get_changes` still defaults to
  `session-start`.

Verified in the dev host:
- a gutter breakpoint, forcing from the watch list, Continue to the
  breakpoint, and step over;
- Pause Claude from the card (Claude's `run_scans` then answers
  `paused_by_user`), and Resume;
- plant parameters applied with a restart;
- adding a watch with Enter;
- Accept on Claude's FB_PI edit.

Revert is covered by a test against the fake CODESYS.

Found while verifying: MCP App views run in an iframe sandbox without
`allow-forms`. That sandbox drops form `submit` events, so the panel uses
click and Enter handlers.

### 10.2 Check results (2026-11-07)

**truST unit tests: usable now.**
- `trust-dev test --project <mirror> --output json` ran 4 tests on the tank
  mirror in about 1 s.
- Results come per test as `passed`/`failed`, with messages such as
  `ASSERT_EQUAL failed: expected 1, actual 2`.
- Supported: `TEST_PROGRAM`, `TEST_FUNCTION_BLOCK`, `ASSERT_EQUAL`,
  `ASSERT_NEAR`, `ASSERT_TRUE` and so on. FB tests, property writes and calls
  through an interface all worked.

Limits:
- Time is frozen inside a test (T1), so a TON never finishes.
- A failure points at the test, not at the assertion (T2).

What this means for Phase 5:
- **`run_tests`** covers logic without time: calculations, state machines
  stepped by inputs, interlock conditions. The toolkit reports results by
  test name and maps lines back where it can.
- **Time-dependent behaviour** (timers, ramps, PI loops) goes through
  **`run_scenarios`** on the simulation (`run_scans`, forces, reads), which
  already steps time exactly. When truST adds time control in tests (T1),
  scenarios can become plain tests.
- **Where tests live:** CODESYS can't hold `TEST_PROGRAM`, so tests live next
  to the project (`<Project>.tests/*.st`) and versioned with it. The mirror
  copies them in at sync.

**trust-lsp: good for structure, not yet for globals.**
- It runs headless over stdio with no client configuration. Its capabilities
  include references, call hierarchy, symbols, hover, definitions and inline
  values.
- On the mirror:
  - **Outline:** the FB with its methods and properties.
  - **Types:** hover (`fbPI : FB_PI`).
  - **Navigation:** go-to-definition across files, and workspace symbol
    search.
  - **References:** locals and FB types across files.
  - **Calls:** incoming calls to an FB, including from tests.
- Missing:
  - references to qualified GVL members (L1);
  - method references and calls, including through interfaces (L2);
  - variables in the outline (L3).

What this means for Phase 5:
- **`get_outline`** parses the exported declarations itself: interface
  sections and types are simple to read from the ST headers, and that's
  reliable today. trust-lsp adds hover types where useful.
- **`find_references` / `get_call_graph`** use trust-lsp for locals, FB types
  and FB calls. For GVL members and methods the toolkit falls back to a
  token-aware text search (qualified names like `GVL_IO.lrLevel` are
  distinctive). The answer is labelled as such until L1 and L2 are fixed in
  truST.

### 10.3 Agreed with truST (2026-11-07)

truST confirmed all six gaps and will implement:
- **Multi-cycle tests (T1).** The test body runs every cycle at a declared
  interval on simulated time until `TEST_FINISHED()` or a cycle budget (as in
  TcUnit and CfUnit). There's no `ADVANCE_TIME()`, because blocks measure time
  between calls. The toolkit asked for:
  - a per-test interval and budget, where exceeding the budget fails the test;
  - a cold restart and simulated time from 0 per test;
  - an optional plant in the loop;
  - tests that call programs, not only FBs;
  - failures with the assertion's line and text, the cycle and simulated time,
    and typed actual and expected values (T2).
- **The `{attribute 'test'}` marker** on an ordinary `PROGRAM` under the
  CODESYS profiles, plus a small `ASSERT_*` library for the CODESYS side.
  Tests then live in the CODESYS project itself, and CODESYS doesn't compile
  them because nothing calls them.
- **Language server (L1-L3):** references taken from the names type checking
  resolved, which covers qualified GVL members, members across files and
  method calls (also in the call hierarchy). The outline becomes a tree with
  variable sections. The toolkit also asked for the access kind (read, write,
  call) on each reference, like the CODESYS cross-reference list.

Changes to Phase 5:
- **Tests live in the CODESYS project** as programs marked
  `{attribute 'test'}`, not in a sidecar folder. Until truST accepts the

- **`get_outline` and `find_references` are built on trust-lsp** after the

  declarations.
- **`run_scenarios` stays** for experiments and closed-loop regressions until
  tests can run with a plant in the loop.
